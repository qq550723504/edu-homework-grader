# AI 出题审核工作台设计

**状态：** 已获用户确认
**范围：** 教师端 `/teacher/ai-questions` 的候选题审核体验重构。

## 目标

让教师在一个页面内清楚回答三件事：正在审核哪一道候选题、它为什么可以或不可以接受、下一步应该接受、修改、重生成还是拒绝。现有生成、验证、审核、批量接受和题库草稿 API 不变。

## 非目标

- 不改变生成批次、候选修订、验证或接受/拒绝的后端状态机。
- 不改变 `blocked`、`warning`、`passed` 的业务含义或接受门禁。
- 不把接受后的题目直接发布给学生；接受仍只创建题库草稿。
- 不新增课程目录、筛选、搜索或新的批量动作。

## 信息架构

页面采用响应式三栏“决策工作台”。

1. 左栏是候选题列表。每项显示序号、简短题目摘要、修订号和可读状态（待审核、有警告、需修改、已接受、已拒绝）。选中项使用现有路由查询参数 `job` 与 `draft`，刷新和深链接行为保持不变。
2. 中栏是题目预览和编辑区。先显示学生可见的题目、选项/阅读材料，再显示教师参考的正确答案、解析、知识点和难度。编辑操作收在“编辑题目”展开区；评分规则 JSON、课程目标 UUID、策略版本和原始验证证据收在“高级信息”展开区。
3. 右栏是审核结论区。它把当前验证状态翻译为中文结论、列出可操作的原因和下一步，并放置唯一的高优先级动作。`passed` 显示“接受为题库草稿”；`warning` 必须先勾选确认；`blocked` 不显示可用的接受动作，只强调修改、重生成或拒绝。

顶部保留“生成新批次”。批量接受保留为折叠的批次工具栏，仅在教师主动展开后显示，不与单题决策竞争。

## 状态与文案

| 验证状态 | 教师可见结论 | 可用操作 |
| --- | --- | --- |
| `passed` | 可以接受 | 接受为题库草稿、编辑题目、重新生成、拒绝 |
| `warning` | 可接受，但请先确认提醒 | 阅读每条提醒、勾选确认后接受；编辑、重新生成或拒绝 |
| `blocked` 或缺少当前修订验证 | 暂不能接受 | 查看阻断原因；编辑后保存并重验、重新生成或拒绝 |
| `accepted` | 已创建题库草稿 | 前往题库工作台；所有写入控件保持只读 |
| `rejected` | 已拒绝 | 保持只读并显示拒绝结论 |

“接受为题库草稿”旁必须说明：接受不会直接发布给学生，仍需在题库中测试和发布。拒绝沿用现有原因和“其他”详情校验。

## 组件边界

- `TeacherAiReviewWorkspace.vue`：维护批次、候选选择、现有 API 写入和批量接受状态；改为编排工作台区域，不复制验证规则。
- `TeacherAiCandidateReview.vue`：成为中栏的候选预览/编辑组件，继续只通过现有事件发出保存、重生成、接受和拒绝请求。
- 新的展示型子组件仅负责候选摘要、审核结论和高级信息的布局；它们接收 `TeacherAiDraft` 与当前 `TeacherAiValidationRun`，不发起网络请求、不持有审核状态。
- 现有 `canAcceptCandidate` 继续作为接受按钮可用性的唯一规则来源。

## 响应式与可访问性

- 宽屏：候选列表、内容和审核结论三栏；审核结论在内容滚动时保持可见。
- 中等宽度：内容与审核结论并列，候选列表移为上方横向/紧凑列表。
- 窄屏：候选列表、审核结论、题目预览依次纵向排列；主要操作全宽，最小点击高度 44px，不产生横向溢出。
- 继续使用语义化 `nav`、`main`、`aside`、`button`、`details/summary` 和可读的 aria 标签；状态不得只依赖颜色表达。
