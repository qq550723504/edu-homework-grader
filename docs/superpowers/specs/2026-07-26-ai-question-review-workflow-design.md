# AI 出题审核工作流界面设计

**日期：** 2026-07-26
**状态：** 待用户审阅
**范围：** 重构教师端 `/teacher/ai-questions` 的信息层级和审核操作呈现，不改变既有生成、校验、审核和入库服务端契约。

## 目标

让教师在审核 AI 候选题时始终能回答三个问题：

1. 这道题位于“生成到发布”的哪一步；
2. 系统为什么允许或阻止接受；
3. 当前应执行哪一个操作。

审核页从堆叠的内部字段和同级按钮，改为引导式工作台。AI 仍只产生候选题；只有教师接受后才创建题库草稿，教师随后还须组卷并发布，学生才会看到题目。

## 现状与根因

当前页面同时展示批次选择、候选编辑、原始评分规则 JSON、校验证据、重新生成、接受、拒绝和批量接受。它没有把“候选题”“题库草稿”“已发布作业”区分成连续阶段，`blocked` 的接受禁用也没有在首要位置解释下一步。

因此教师需要自行推断：批次是什么、题目为何不可接受、修改后是否重新校验，以及接受是否会立即让学生看到。问题属于信息架构和动作优先级，而不是 API 或审核状态机缺失。

## 采用方案

采用“引导式审核工作台”。左侧保留批次与候选题浏览，右侧固定为题目预览、系统结论、教师下一步三个区域；顶部显示端到端进度。

未采用的方案：

- 仅调整现有表单顺序：改动小，但教师仍需在长页面中寻找结论和动作；
- 全屏逐题向导：单题专注，但丢失同批题目比较、状态总览和批量接受入口。

## 页面结构

### 顶部进度

显示五个只读阶段：`生成批次 → 系统校验 → 教师审核 → 题库草稿 → 组卷并发布`。当前页固定突出“教师审核”。进度只解释业务位置，不表示可点击的导航或绕过状态机的控制。

### 左侧批次导航

保留现有任务和候选题选择能力，并以教师可理解的状态汇总：

- 待处理；
- 可以接受；
- 需修正；
- 已接受；
- 已拒绝。

每个候选项继续使用现有 job、draft、revision 查询参数作为权威选择来源。状态汇总是读取现有 `teacher_state` 和最近 validation run 的派生展示，不在浏览器持久化新的审核状态。

### 右侧审核主区

按固定顺序展示：

1. **学生将看到的题目**：题干、阅读材料（仅 E4）、知识点、题型与目标难度；
2. **系统审核结果**：面向教师的状态标题、原因和建议动作；
3. **教师下一步**：由当前状态决定的主次操作；
4. **修改题目**：按需展开，包含题干、参考答案、解析、知识点、难度及 E4 阅读材料；
5. **高级信息**：按需展开，包含评分规则 JSON、稳定 finding code 和已脱敏证据。

原有字段、校验记录和版本数据仍可访问，但不抢占学生视图和审核结论的位置。

## 状态与动作

| 校验与审核状态 | 首要结论 | 允许的动作 |
| --- | --- | --- |
| `blocked` + `pending_review` | 需修正，不能接受 | 修改并重新校验、重新生成、拒绝 |
| `warning` + `pending_review` | 需要教师确认 | 阅读 warning 后接受、修改并重新校验、拒绝 |
| `passed` + `pending_review` | 可以接受 | 接受为题库草稿、修改并重新校验、拒绝 |
| `accepted` | 已创建题库草稿 | 前往题库工作台；不再提供写操作 |
| `rejected` | 已拒绝 | 仅展示结果和审计信息；不再提供写操作 |

“修改并重新校验”调用现有保存修订请求；服务端返回的 `validation_run` 是修改后的权威校验结果。单题重新生成继续创建新任务并保留来源候选和审计记录。任何 `blocked` 状态都不能通过前端控件绕过接受。

## 批量接受

批量接受由每道题的“加入批量接受”意图汇总而来：

- 只有 `pending_review` 且 `passed` 的候选能直接加入；
- `warning` 候选必须逐项确认已阅读 warning；
- `blocked`、已接受和已拒绝候选不可选；
- 按钮文案显示已选数量与结果：`接受已选 N 题为题库草稿`；
- 保持现有服务端 all-or-nothing、CSRF 和 Idempotency-Key 语义。失败时保留选择并显示权威错误，不假定部分成功。

## 数据流与错误处理

页面继续通过既有 `TeacherAiReviewWorkspace` 读取 jobs、drafts、candidate 和 validation。UI 不自行判断最终接受资格：它仅根据服务端状态呈现建议，接受、拒绝、保存修订、重生成和批量接受仍由现有 API 与服务端状态机授权。

网络未知结果、409 状态变更、403/404 权限或不存在、503 服务不可用，继续走现有 `publicErrorMessage` 和刷新机制。重新加载后以服务端状态覆盖临时展示。页面不得展示 Provider 密钥、系统 Prompt、私有验证特征或未脱敏记录。

## 组件边界

- `TeacherAiReviewWorkspace.vue`：路由选择、批次汇总、写入协调、批量选择和顶层工作台布局；
- `TeacherAiCandidateReview.vue`：候选预览、状态化审核结论、编辑区域和单题操作；
- 新的展示型子组件可提取进度条、批次状态摘要和审核结论卡，但不得复制 API 访问或接受资格逻辑；
- `teacher-ai-review.ts`：保持 API 客户端和类型职责；不因视觉重构改变接口。

## 测试

Vitest 渲染测试覆盖：

- 五阶段进度和当前审核阶段；
- 批次/候选状态汇总及选择；
- `blocked`、`warning`、`passed`、`accepted`、`rejected` 的中文结论与可用动作；
- warning 确认后才可接受；
- blocked 不能加入批量接受；
- 修改区域与高级技术记录的展开/收起；
- 接受后明确说明“已创建题库草稿”，而非学生已可见；
- 已有保存、重生成、拒绝、单项接受、批量原子失败和错误映射回归。

Playwright 继续覆盖生成至批量接受、单题重生成和接受后进入题库草稿的端到端流程，并增加可见流程文案断言。完成后运行相关 Vitest、Playwright 与 Nuxt build。

## 非范围

- 不修改 AI Provider、Prompt、配额、生成计划、验证规则、审核状态机或题库/作业 API；
- 不让教师从审核页直接把题发布给学生；
- 不新增成本估算、任务轮询、模型灰度或新的数据表；
- 不改变现有班级、作业、题库或学生端流程。
