# AI 生成默认配置治理设计

**日期：** 2026-07-28  
**范围：** GitHub #43 的默认模型/Prompt 受控晋级与回滚子域

## 目标与边界

为 AI 题目生成建立完整、可审计的默认配置生命周期：评估通过后提出变更、独立审批、原子晋级、历史可追溯、受控回滚。教师侧不新增选择器、草稿或复杂工作台；平台治理页只展示当前默认、待审批变更和历史记录。

本设计只覆盖全局默认的 `provider + immutable model + prompt` 组合。现有租户级 `active/canary/paused/retired` 控制仍作为运行时准入门禁，但不用于覆盖默认配置。预算告警、供应商合规、版权投诉与事故流程仍是 #43 的独立子域。

## 根因

当前默认 Prompt 是服务常量，默认 OpenAI 模型来自部署环境变量。变更二者需要改代码或环境并重启，数据库无法回答“谁依据哪份评估批准了这次切换”，也无法可靠回滚。现有 `GenerationGovernanceEntry` 只表达组件是否可用；把“可用”和“当前默认”混为同一条记录，会让灰度、停用和审批历史相互覆盖。

`GenerationJob` 已保存 Prompt 版本，`GenerationAttempt` 已保存实际 provider/model/Prompt；但模型直到执行时才解析，故创建任务与实际调用之间仍可能受环境变量变更影响。默认选择必须在创建任务时被快照，而非由运行时设置隐式决定。

## 采用的架构

借鉴成熟变更控制的“提交—审批—应用”模式：配置控制面保存不可变变更记录，运行面只解析一条已生效的默认选择。它与 OpenFeature 的“评估接口”和控制平面解耦思路一致，但不引入新的特性开关服务；继续使用本项目的 SQLAlchemy、FastAPI 和防篡改审计链。

### 1. 不可变配置快照

新增 `GenerationDefaultConfiguration`，每行代表一个可复现的候选组合：

- `provider_name`；
- `model_version`，OpenAI 时必须通过既有不可变模型 ID 校验；
- `prompt_version` 与从 Prompt 目录解析出的模板指纹；
- 创建时间与创建人。

配置行创建后不得修改或删除。相同 provider、模型、Prompt、模板指纹可复用同一配置行；模板指纹使版本名被错误复用时不能静默改变语义。

### 2. 评估证据与变更请求

新增 `GenerationDefaultChangeRequest`，状态仅为 `pending_approval`、`approved`、`rejected`、`applied`、`superseded` 与 `rolled_back`。不提供“草稿”状态或草稿界面。

提交人必须提供完整的 `OperationalEvaluationReport` JSON。服务端以现有 Pydantic 模型重新校验，并拒绝：

- `promotion_eligible != true`；
- 报告候选 provider、模型或 Prompt 与请求配置不一致；
- 报告的记录摘要、运行 ID、规格 ID 或水位线缺失；
- 目标 Prompt 无法从本地目录解析，或目标模型不是固定快照；
- 任一目标组件被全局暂停或退役。

服务端保存经规范化后的报告摘要、报告 SHA-256、记录摘要、run/spec ID 和水位线；不保存候选题目正文、教师身份或其他评估原始数据。这样审批记录直接绑定可验证评估输出，而不是自由文本“已评估”。

### 3. 独立审批与原子应用

平台治理管理员提交变更；另一名平台治理管理员才可批准或拒绝。审批必须写明决定说明。提交人不得审批自己的请求，避免单人绕过评估与复核。

批准本身不切流。`apply` 只接受已批准且尚未处理的请求，并在同一数据库事务内：

1. 锁定全局默认选择；
2. 重新校验候选配置、评估证据及治理状态；
3. 将选择指针切到候选配置；
4. 将请求标记为 `applied`，将旧生效请求标记为 `superseded`；
5. 追加审计事件。

`GenerationDefaultSelection` 只保存当前配置 ID 与最后应用请求 ID，数据库唯一约束保证全局恰有一行。默认值切换不会通过直接更新配置或历史请求完成。

### 4. 回滚

回滚以一个已生效历史请求为目标，必须填写原因和审批证据引用。系统先创建一条新的 `pending_approval` 回滚请求，复用目标配置和其经验证的评估证据；另一位治理管理员批准后再应用。原请求不改写，仅将该次新决策标记为 `rolled_back` 并关联被回滚的生效请求。

这保证每一次“回到旧版本”也有独立的操作者、理由、审批人与审计时间，而不是直接编辑默认值。

### 5. 运行时解析与历史不可变性

创建 `GenerationJob` 时，服务读取已生效的全局选择，并将 `provider_name`、`model_version`、`prompt_version`、模板指纹写入 Job。执行时仅按 Job 快照构造 provider，并再次执行现有全局/租户治理准入校验。

因此后续默认配置、环境变量或 Prompt 目录变化均不影响已创建 Job；`GenerationAttempt` 继续记录真实调用结果，并要求其配置与 Job 快照一致。缺少生效选择时，生产环境失败关闭并返回稳定错误码；部署流程必须先用受保护的初始化请求建立首个经审计的默认配置。测试与开发环境使用显式 fixture 初始化，不保留环境变量静默回退路径。

## API 与界面

平台治理管理员专用端点：

- `GET /v1/admin/ai-generation-defaults`：当前默认、待审批请求和历史请求的脱敏摘要；
- `POST /v1/admin/ai-generation-default-change-requests`：提交评估通过的候选配置；
- `POST /v1/admin/ai-generation-default-change-requests/{id}/approve` 与 `/reject`：独立审批；
- `POST /v1/admin/ai-generation-default-change-requests/{id}/apply`：应用已批准请求；
- `POST /v1/admin/ai-generation-default-change-requests/{id}/rollback`：基于历史生效请求提出回滚。

界面只在现有管理员治理入口增加一个页面：顶部一张“当前默认”卡片；其下为待审批列表和不可编辑的历史表；提交、审批、应用、回滚均使用简短确认表单。普通租户管理员与教师看不到端点、模型 ID、评估摘要或系统 Prompt 内容。

## 权限、错误处理与审计

- 继续使用现有平台治理 subject allowlist；业务上新增“非本人审批”校验。
- 所有写操作使用幂等键与请求摘要，重复提交返回原结果；同一请求不允许二次应用。
- 失败关闭错误码区分：无生效默认、评估未通过、评估与候选不匹配、组件被治理状态阻断、非独立审批、请求状态冲突。
- 每个提交、批准、拒绝、应用和回滚写入现有 HMAC 审计链。元数据只含 UUID、版本标识、摘要、状态和原因，禁止写入题目正文、Prompt 正文、密钥、邮箱或 OIDC subject。
- 并发应用依赖行锁与状态条件更新；一个请求至多应用一次，最终只存在一个全局默认选择。

## 迁移与部署

新增迁移创建三个表及约束：不可变配置、变更请求、单行默认选择。迁移不从部署环境变量猜测或写入生产默认模型。部署顺序为：运行迁移、由两名授权治理管理员完成首个初始化请求与审批、验证默认选择和审计链、再允许生产生成流量。

现有生成记录不回填。为避免未配置环境继续产生不可追溯的任务，运行时在没有默认选择时失败关闭；部署文档和健康检查明确报告该状态。

## 验收与测试

- 仅固定模型 ID、已解析 Prompt 和 `promotion_eligible=true` 的匹配评估报告可提交。
- 自己提交的请求不能由本人批准；未批准、被拒绝、已处理或被治理暂停的请求不能应用。
- 应用一次后，新 Job 固化 provider/model/Prompt/模板指纹；后续切换或环境变量变化不改变旧 Job 与 Attempt。
- 回滚创建新的、需独立审批的决策记录，并能恢复目标历史配置而不改写历史。
- 并发 apply、重放 idempotency key、无默认选择、报告篡改和模型/Prompt 不匹配均有稳定失败结果。
- 管理 API 与页面不泄露 Prompt 正文、评估记录正文、密钥或身份敏感字段。
- 迁移、服务、路由、审计、权限和最小管理员 UI 均有单元/集成测试；关键晋级—生成—回滚链路有浏览器端到端测试。

## 非目标

- 不在本次实现预算/并发告警、Provider 合规证明、投诉处理或事故响应。
- 不支持租户级默认覆盖、百分比路由或自动晋级。
- 不把离线评估程序改造成在线模型调用；本功能只验证并保存其已产生的合格报告。
