# 学生账号与一次性激活码设计

## 目标与范围

教师已能维护班级名册，但名册记录不是可登录账号。本功能让教师为自己班级中尚未绑定身份的学生批量创建登录身份，并交付一次性激活码。学生以“学号 + 激活码”完成首次登录，在 Keycloak 中自行设置长期密码。

首个交付包含：为已有名册学生批量签发或重置激活码、一次性 CSV 下载、Keycloak 用户创建和角色分配、过期与审计，以及生产 Keycloak 配置的幂等同步。CSV 导入仍只导入名册；导入完成后由教师显式选择学生签发账号。这样可以避免把明文凭据写入导入文件、日志或长期数据库。

不包含邮件或短信发送、公开注册、家长账号、学生自助找回密码，或由教师保管长期密码。

## 方案选择

采用“激活码即 Keycloak 临时密码”的方案。它复用现有 OIDC 登录和 Keycloak 的强制改密能力，学生不需要新页面或额外的凭据交换协议。

没有采用以下方案：

- 应用自建激活页面再调用 Keycloak 重置密码：可以精确控制过期时间，但会新增一套涉及密码的认证流程，容易与现有 OIDC 会话脱节。
- 为每位学生生成并长期保存初始密码：实现简单，但教师和数据库能反复取得明文凭据，不符合一次性交付的安全边界。

## 架构与职责

### API 和数据模型

新增学生激活记录（每名学生可保留历史记录，只有一条处于待激活状态），至少包括：学生 ID、班级 ID、Keycloak 用户 ID、状态、激活码 HMAC、签发/披露/过期/使用/撤销时间、签发教师与请求 ID。数据库绝不保存激活码明文；HMAC 密钥从 Kubernetes Secret 注入。

状态为 `provisioning`、`issued`、`consumed`、`expired`、`revoked` 或 `failed`。请求在数据库中先预留 `provisioning` 记录，再调用 Keycloak，避免外部调用被包在不可控的数据库事务里。Keycloak 调用失败时记录失败原因（不含凭据）并允许教师重试；网络中断时按请求 ID 和学号查询既有 Keycloak 用户，防止重复创建账号。

新增教师授权的批量签发接口，仅接受该教师所属班级中未绑定或尚未激活的学生 ID。接口：

1. 验证教师、班级归属、学生归属、学号唯一性及绑定状态。
2. 为每名学生生成高熵、符合 Keycloak 密码策略的激活码；创建或更新 Keycloak 用户（`username` 为学号，`school_id` 属性为相同值），赋予 `student` realm role，并将密码设为 temporary。
3. 写入不含明文的激活记录。成功项目以 `text/csv` 响应返回；失败项目返回明确但不含敏感数据的行级错误。

CSV 包含班级、学生姓名、学号、激活码和过期时间。响应必须带 `Cache-Control: no-store`、附件下载头和日志脱敏。前端只在内存中创建下载 Blob，随后立即释放，且不写入浏览器存储。服务在返回响应前标记 `disclosed_at`；明文在该请求后不可恢复。下载中断或遗失时，教师只能签发新码，旧码立即撤销。

已绑定且已使用正常账号的学生不能通过此接口重置密码；该类需求以后由学生自助找回流程处理。

### Keycloak 集成

新增专用 `student-provisioner` 服务账号客户端。API 仅挂载此客户端的凭据，并仅拥有学生用户所需的最小 realm-management 权限（查询/管理用户，以及读取/分配既有 `student` 角色）。它不拥有管理 realm、客户端或管理员账号的权限。

应用通过一个独立的 Keycloak Admin 适配器调用管理 API；路由、名册服务与数据库模型不直接依赖 HTTP 细节。适配器负责按学号查找用户、幂等创建、设置 `school_id`、分配角色和设置临时密码。

生产环境已有 realm 因 `IGNORE_EXISTING` 导入策略而不会自动应用 `realm.json` 变更。因此部署增加一个受运维 Secret 保护的、一次性且幂等的 realm 同步 Job：它声明 `student`、`teacher` 角色、允许管理员写入的 `school_id` 用户资料字段、所需 mapper 与受限服务账号。该 Job 的高权限凭据只挂载到 Job，绝不挂载到 API/Web/Grader 容器，也不提交到仓库。运行完成后，日常签发只使用 `student-provisioner` 的受限凭据。

## 激活、过期与重置

激活码有效期固定为 7 天。首次 OIDC 回调发生在 Keycloak 强制改密之后；API 在创建本地会话前检查待激活记录：未过期则标记 `consumed_at`，已过期则拒绝建立应用会话。这样过期码即使尚未被后台清理，也无法进入应用。

定时清理任务至少每 5 分钟处理过期未使用记录：将 Keycloak 临时密码替换为未知随机值，并标记记录 `expired`。这缩短 Keycloak 层仍可能接受旧临时密码的窗口；应用回调检查提供立即的访问阻断。重新签发时先在 Keycloak 重置密码，再把先前 `issued` 记录标为 `revoked`，然后签发新记录。仅签发成功的明文会出现在当前 HTTP 响应中。

每次签发、披露、使用、过期、撤销和失败都写入审计日志，包含操作者、目标学生、时间和请求 ID，不含激活码或密码。

## 错误处理与一致性

批量请求逐项处理，不因一名学生数据错误而丢弃其他已成功创建的账号。响应同时列出成功下载数据和无敏感信息的失败行。出现部分成功时，教师可仅重试失败学生；任何已签发码都不可读取，只能重置。

已绑定到不同 OIDC subject、学号重复、学生不属于该教师班级、缺失同意记录或 Keycloak 角色/用户资料配置不完整时，接口拒绝对应项目并留下可诊断审计事件。所有异常响应和结构化日志都禁止包含验证码、临时密码、客户端密钥或管理员凭据。

## 前端体验

教师名册页在“未绑定”学生行和批量选择栏提供“生成激活码”。提交前显示学生数量、7 天有效期和“下载后无法再次查看”的确认提示。成功后浏览器自动下载 CSV，并显示成功/失败数量与“遗失请重新生成”的说明。已绑定学生没有该操作入口。

## 验证策略

- API 单元测试覆盖教师授权、班级边界、学号唯一性、状态转换、明文不落库、重置撤销和过期拒绝会话。
- Keycloak 适配器测试使用 HTTP 假服务，验证请求不重复创建用户、设置角色/属性/temporary 密码，以及错误脱敏。
- 路由集成测试验证 CSV 头、`no-store`、部分失败返回和审计记录。
- 前端测试验证批量确认、一次下载和已绑定学生无操作入口。
- Kubernetes/realm 配置测试验证角色、用户资料、mapper、服务账号 Secret 挂载范围和同步 Job 幂等输入。

## 验收标准

1. 教师可为自己班级的一名或多名未绑定学生生成激活码 CSV，系统不持久化或记录明文。
2. 学生可用学号和激活码登录，并被强制设置新密码；之后旧码不能再次使用。
3. 过期码立即不能建立应用会话，并会在 5 分钟内在 Keycloak 侧被失效处理。
4. 遗失码只能通过重新签发恢复，旧码立即失效；已绑定学生不会被该功能改密。
5. 所有生产凭据来自最小权限的 Kubernetes Secret，应用容器不持有 Keycloak 管理员凭据。
